# Durable continuation mutation receipts

The existing SQLite child-session repository retains each prepared mutation identity before attempting its state transaction. The state change and original result receipt commit atomically. This is local SQLite acknowledgement; it does not establish PostgreSQL replication, another execution owner's death, or host fencing.

`PreparedContinuationMutation` contains canonical immutable JSON bytes, child ID, operation kind, operation ID and a SHA256 digest covering kind, child and arguments. An operation ID identifies a write; it grants no permission. Existing `create`, `save_checkpoint`, `update`, `claim_resume` and `request_cancel` methods remain available and prepare a fresh identity once per call. A caller reconciling an uncertain attempt must retain and use its original prepared identity, not invoke a canonical method again.

`mutate(prepared)` returns an immutable original result receipt. Matching replay returns that original result even after the child advances. Changed input under the same operation ID is rejected. A failed CAS and a no-change cancellation also have receipts. `reconcile(prepared)` is read-only: a receipt proves the local committed result; `None` means unresolved, never proof that the operation did not happen. `read_mutation(operation_id)` retrieves the exact durable intent. `mutation_ids(child_id, after=position, limit=1..100)` pages retained identities; its returned boolean describes further IDs in that child scope. `unresolved_mutation` retrieves the earliest pending identity, while `latest_mutation` is diagnostic and does not replace inspection of older operations.

The service refuses new writes, launch and result delivery when a child has unresolved storage state. Storage failures stop its worker's continuation path without synthesizing a retryable runner failure. Cancellation is cooperative: arbitrary runner code that ignores cancellation cannot be forcibly stopped by this storage boundary. Service shutdown still joins owned threads and preserves uncertainty.

After restart, RUNNING children are not automatically marked failed or made resumable. The old process might still own effects, or a checkpoint/terminal acknowledgement might have been lost. Their RUNNING state remains intact pending independently proven cleanup and receipt reconciliation. This stage provides inspection and exact storage replay primitives, but no operator force-resume command or cleanup authority. An unresolved resume intent also blocks launch when the older persisted row still says FAILED. A settled terminal receipt can be read after reopen without rerunning the child.

SQLite adds `continuation_intent` and `continuation_receipt` alongside the canonical child table; it does not copy child state into another task ledger. Existing child rows remain readable. Additive schema creation is automatic when opening the repository. Older binaries can read the child table, but must not be used to run children while unresolved intents exist: they lack the new guard. Rollback therefore requires stopping the owner and resolving pending operations, not just swapping binaries.

Bounds are 100,000 retained intents/receipts, 64 MiB of combined payload/result bytes, and 2,000,000 bytes per serialized payload or result. Tests may configure smaller positive repository bounds. These bound stored payloads, not total SQLite file/index size or peak JSON serialization memory. Capacity exhaustion fails closed without pruning history. A result-capacity failure rolls back the state transaction and leaves its already retained intent unresolved. There is no automatic retention deletion; increasing a test-lowered capacity within the maximum permits exact-ID reconciliation. Production retention/archival remains a future explicit operation.

The existing application composition continues selecting SQLite with the existing child-session database setting. Budgets, permission checks and provider-owned roots are unchanged. This stage does not select PostgreSQL or permit concurrent execution controllers; distributed admission and authority remain outside this receipt boundary.
