# Opt-in Linux Codegen container build

Active Codegen canaries require a lower-privilege build worker before the host
reserves the project or sends a model request. The host composes one only on
Linux with an already-running local Docker or Podman engine and an exact,
locally installed image ID. The default is off. Windows remains unsupported;
the low-integrity self-modification runner is not a Codegen build adapter.

Set all of the following host-owned settings before selecting the existing
`SONDER_STRATEGY_MODE=canary` rollout:

| Setting | Required value |
| --- | --- |
| `SONDER_ISOLATED_RUNTIME` | `docker` or `podman`, with a responsive local Linux engine. |
| `SONDER_ISOLATED_ROOTS` | The private staging directory (or a host-approved parent). |
| `SONDER_CODEGEN_BUILD_PROJECT` | Canonical absolute path to exactly one authorized project. |
| `SONDER_CODEGEN_BUILD_STAGING_ROOT` | An existing directory owned by the service user, mode `0700`, outside the project and runtime state home. |
| `SONDER_CODEGEN_BUILD_IMAGE` | The local reviewed image ID, `sha256:` followed by 64 lowercase hexadecimal characters. Tags are refused. |
| `SONDER_CODEGEN_BUILD_ALLOWED_SOURCES` | JSON array of exact relative source paths the host permits Codegen to generate and compile. Model-declared sources must be a subset. |
| `SONDER_CODEGEN_BUILD_INPUTS` | Optional JSON array of exact additional build files, such as `project.csproj`. These are copied but never generated by Codegen. |

The pinned image must contain `/usr/bin/env` and the fixed
`/usr/local/bin/sonder-codegen-launch` built from
`scripts/codegen_container_launch.c`, plus the desired offline toolchain.
The dedicated qualification workflow compiles the launcher and a simple C
staging probe from checked-in source into a local `FROM scratch` fixture. The
probe reads staged source and writes a disposable output; it is not a compiler
and does not test a production toolchain. The workflow does not attest an
operator's separate production image or install one. Its image ID is obtained
from the local engine; no runtime pull is permitted.

At each build, the trusted host reads the exact granted files through
no-follow descriptors, rejects symlinks, hardlinks, cross-device paths,
selected nested mounts and non-regular entries, and copies at most 256 files,
4 MiB per file and 16 MiB total. Missing generated files are allowed for the
initial build; missing additional host-granted inputs refuse. No hidden path,
strategy state filename, common credential suffix or private directory name
can enter the manifest. The operator must inspect granted file contents:
allowlisting a source file that *contains* a credential still grants its bytes
to the build process.

Only that disposable source snapshot is mounted, read-only, into `/workspace`.
The fixed image launcher copies it into `/build/project` on a 1024 MiB tmpfs;
build writes do not touch the host project or fill a host bind. The container
has no network, no inherited environment or host home, no engine socket,
an unprivileged UID/GID, no Linux capabilities, no-new-privileges, a read-only
image root, and fixed process, CPU, RAM and wall limits. The underlying engine,
image, kernel and their isolation implementation are trusted infrastructure.

The host owns the process exit status and rejects output overflow, timeout,
launch failure or unverifiable container removal. Reserved daemon/launcher
exit statuses and signal-like exits never count as compiler feedback. The
native probes include a missing build executable. On uncertain removal the
host retains the disposable read-only snapshot and the Codegen project guard
for operator reconciliation. Diagnostic text remains candidate-controlled:
projects can include build scripts that print false diagnostics or exit zero.
A successful build is therefore neither an independent task grade nor a
promotion/deployment authorization. Compiler/toolchain quality, live workload
coverage and real operator image qualification remain separate obligations.

The new Linux workflow `codegen-container-qualification.yml` builds a hermetic
local image and requires four real Docker probes with zero skips. They cover
actual read denial for dummy key, database and SQLite sidecars, environment
scrubbing, undeclared source exclusion, host process denial, read-only host
source, refusal of external connection and a loopback-only network namespace,
unprivileged process state, bounded disposable staging output, nonzero probe status,
symlink refusal and timeout cleanup. This is native fixture evidence, not a
proof against a compromised kernel or a certificate for other images.
