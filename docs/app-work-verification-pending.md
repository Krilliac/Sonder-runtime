# Durable app verification approval waits

`WorkVerificationPending(identity, approval, original_terminal)` retains an exact `PendingVerificationIdentity`, an actual `PendingApprovalEvidence` for `workspace_run`, and the original sealed host terminal link. It contains no approval nonce, bearer, or reconstructed execution authority. The caller is trusted host composition: it must first obtain current eligibility through the existing guarded verifier/host APIs. There is no public endpoint accepting these records.

`AppControlTransaction.record_work_verification_pending(pending=..., **scope)` uses the existing principal/control/work/dispatch/process/expected-revision scope. It changes only RUNNING revision4 to verification_pending revision5 in the same protected fleet transaction. Exact retry returns the retained current record, including after later unknown/terminal transitions; conflicting identity, approval deadline, original receipt or scope refuses. New observations of an already expired approval refuse; historical reads and identical retries never renew that expiry or claim resumability.

`verification_pending` is non-dispatchable and continues to occupy the binding's active-work slot. `admit_work` replay remains newly_admitted=False. Unknown transitions may preserve this prior phase and all its original evidence. Later completion must retain the exact original terminal link and the same verification identity with typed certified/certified_after_return publication evidence. It cannot turn into not_required or discard the pending link. A completed row retains the pending observation as history; only its separately proven completion permits another work record.

Host and verification projections can have different sealed bindings and digests. This port intentionally does not equate their digests. It checks shared continuation/parent and exact retained host turn; trusted composition must run `require_host_pending_turn` through the existing eligibility service to compare the original decoded draft and verifier binding before recording this observation. Stored metadata never substitutes for fresh live account, selection, attachment or verifier checks.

Absent metadata is omitted from canonical serialization, preserving historical byte representations. Historical absence means unknown/not recorded, never inferred approval or completion. Decoding remains strict and bounded, including exact typed records, unknown fields, duplicate JSON keys, original host scope, approval digest/display identity and valid finite timestamps. Existing protected-schema, same-connection borrowing, write/readback and transaction rollback behavior remains unchanged.
